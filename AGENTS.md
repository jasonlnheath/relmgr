## Cache discipline (2026-09-26, repeated false phone regressions)

- ALL HTML responses carry `Cache-Control: no-cache, must-revalidate` via `_security_middleware` in app.py (one spot) — Safari had served stale pages after deploys and masked fixes as "phone-only regressions".
- `/static/*` is immutable long-cache AND every template reference is versioned `?v={{ asset_v('name') }}` (`_static_version`, a Jinja global): content changes change the URL. `tests/test_cache_headers.py` fails on any unversioned `/static/` reference.
- Tailwind is SELF-HOSTED: `static/tailwind-3.4.17.js` (the Play CDN build, same-origin, immune to iOS content blockers / CDN drift / 4h phone caches of cdn.tailwindcss.com). Upgrading = vendor the new build into static/ and repoint the `<script>` in base.html. Google Fonts (Arapey) stays remote (cosmetic, Georgia fallback).
- `/photos/*` and `/qr/*` mutate in place under the same URL → `no-cache` (their ETag/Last-Modified make revalidation a cheap 304).
- The live server for the captain's phone runs from the primary checkout (`/home/jason/relmgr`) on 0.0.0.0:8099, started by a prior task's worker; verify its checkout with `git -C /home/jason/relmgr rev-parse HEAD` and read `/tmp/relmgr.log` before diagnosing phone reports — but never modify the primary checkout from a task worktree.

## Architecture sharp edges

- Module layout (2026-09-26 refactor): `app.py` is the composition root (middleware, static mount, boot heal, route registration); every route group lives in a `routes_*.py` module registered via `register_*_routes(application, ctx)`; shared helpers + `WebContext` live in `web_support.py`. Tests import helper names from `app` (re-exported) and patch `app._send_connection_request_email` BEFORE create_app — `WebContext.push_connection_email` is read from app.py's namespace at create_app time to keep that patch surface working. See `docs/CODEMAP.md` §2.

- Whitelist DB schema changes go through ONE ordered entry point: `whitelist_db.ensure_whitelist_schema` (order is load-bearing). Additive tables/columns get their own idempotent `ensure_*` function called there. SQLite cannot ALTER a CHECK constraint — extending an enum CHECK (profile_fields field_type, grant_logs actions, notification kinds) means the row-preserving table-swap heal pattern (see `ensure_vcard_fields_pass3_schema`, `ensure_notification_kinds`, `ensure_grant_log_actions`).
- Access tiers: `effective_tier()` is the single tier oracle ('granted'/'anonymous'); public surfaces must filter fields through the `visible_fields` pattern in `cards_for_public_view` / `cards_for_share_bundle` (anonymous = public fields only; granted = public+granted+private). Revoked == blocked == blacklisted, one state.
- Silence rule (captain ruling 2026-09-20): contacts are NEVER notified about badge moves, quarantine, or their own status; notifications (`notifications` table) are owner-only. Blacklisted senders' requests go to `quarantined_requests` with an indistinguishable success page.
- Share bundles: one stable link `/s/{id}` per chosen card set; fields render live from card IDs; links expire 7 days after creation (`expires_at`). F4 ruling (2026-09-23): links ALWAYS deliver the PUBLIC-facing page (anonymous tier, no exceptions — even for connected viewers) and ALWAYS include the bio (pass 3); more access goes through the Connect request flow. UX pass 3 (2026-09-23): the chooser/reshare OWNER routes are RETIRED — bundles are minted at the data layer only (`create_share_bundle`); My Profile carries the QR + native Share button (`navigator.share`).
- Card ordering (pass 3): Personal first, Work second, rest alphabetical — ONE SQL fragment `_CARD_ORDER_SQL` used by `list_cards`/`cards_for_public_view`/`cards_for_share_bundle`. `seed_default_cards` ALWAYS creates the Personal+Work pair for every profile (even empty); legacy names (Identity/Contact/…) are heal-only. The top (Personal) card is the default public picture; shared sets lead with Personal (`card_kind`).
- Style ruling (captain 2026-09-22, pass 2 extends it): grey EVERYWHERE — no green, red, or blue (and no amber) action buttons; `.wl-btn-approve`/`.wl-btn-deny`/`.wl-btn-revoke`/`.wl-btn-punt` are all aliases of the default slate gray (see `templates/base.html`); status color lives only in badges/text. Share icons use an ink `currentColor` SVG, never the red-rendering 📤 emoji. Badge toggle confirmations say the list names WhiteList/GreyList/BlackList, never the internal 'blocked'.
- Card editor UX: removing a field is an immediate per-row ✕ POST (`/owner/{token}/cards/{id}/fields/{fid}/delete`). The ✕ posts the WHOLE editor form (formaction override), and the delete route MUST apply the full parsed body (`_parse_editor_form` in routes_editor.py, shared with the save route) together with the removal — ignoring the body was a real data-loss bug (pass 2). Card-editor form parsing has ONE entry point; both routes must use it. Field rows are ALWAYS one line (`flex flex-row items-center` — pass-9 ruling, restored 2026-09-26 after the pass-4b consolidation reverted it to `flex-col sm:flex-row`, dropping dropdowns/✕ below the field on phones); the pass-9 mobile-squeeze CSS (`span.w-28` 56px, ✕ 24px, select min-width 60px in base.html) is sized for that one-line row — do not reintroduce stacked rows. Photos are CIRCLE-cropped client-side (disc composited on the `#1A1A1C` backdrop, stored as square JPEG; every display surface clips with `rounded-full`).
- Address blocks render for EVERY card scope (`ADDRESS_BLOCK_SCOPES` = vcard+personal+work, 2026-09-26): the new-connection flow lands in the stub's WORK editor when an email was provided, so work-scoped editors must show the grouped six-input blocks + `+ Add address` too. All `_SCOPE_TEMPLATES` Addresses sections use heading 'Addresses' with the six block components (legacy flat `CARD_EDITOR_SECTIONS` heading 'Address Block 1' deliberately never matches the block branch).
- Contact-list badge cycle White→Grey→Black is `whitelist_db.set_badge_state` — grey stamps `expires_at = quarter_end_iso()`, an INTERNAL marker that feeds the quarterly prompt, never an expiry (see next); treat it as the single state-cycle entry point.
- Semantics ruling (captain 2026-09-22, pass 2; enforced in code after the pairing review): greylist/blacklist contacts NEVER expire — `_ADMITTED_EXPIRY_SQL` (whitelist_db.py, next to `_LIVE_GRANT_EXPIRY_SQL`) is the admission predicate used by BOTH `effective_tier` and `create_grant` dedupe: status='granted' + any real-timestamp expiry admits forever; legacy '14d' strings still never leak. `_LIVE_GRANT_EXPIRY_SQL` remains only for non-admission display logic (logo freshness). No 'Expires' row in any UI; the quarterly review confirms/updates contact info and reviews grey/black contacts — never deletes. `sync_quarterly_notifications` carries the wording.
- Field visibility defaults: everything defaults 'granted' EXCEPT the public set — pass 2: title/company/website (+bio); pass 3 adds birthday, high_school, maiden_name, nickname, city, state, childhood_city, childhood_state. Street-level addresses (address1/address2/zip/childhood_address1) stay granted. One decision table, TWO mirrors: `_PUBLIC_DEFAULT_TYPES`/`_PRIVATE_DEFAULT_TYPES`/`_editor_default_visibility` in routes_editor.py + `public_default_types`/`private_default_types`/`default_visibility` macro in card_editor.html (the old unused whitelist_db mirror was removed 2026-09-26). F3 (2026-09-23): the pass-2 defaults were BACKFILLED once via `ensure_pass2_visibility_heal` — later explicit edits are never re-healed, and pass-3 default changes deliberately did NOT backfill.
- Grey state (pass 3 bug fix): `is_grey` = granted + any real-timestamp `expires_at` (future marker INCLUDED — badge-moved grey contacts render GreyList on the contact card, agreeing with the list). The quarterly digest (`get_grey_contacts`) stays lapsed-only.
- Notifications (pass 3): the notifications PAGE/routes/header button are eliminated; the `notifications` TABLE + data layer remain (append-only event record, email push's source of truth; `sync_quarterly_notifications` still runs on the dashboard). Requests surface in the AMBER box at the top of the contact list (`pending_rows` → contact_list.html).
- Curated stub profiles: `create_contact_vcard` stamps `profiles.owner_id` = creating owner and leaves password_hash NULL; `_resolve_editor_card` lets that owner edit the stub's cards (create lands in the new vCard's editor) — other accounts 404, and a set password closes the stub again. The card editor renders the CARD-owner profile's name.
- Template dedup (2026-09-26): shared field-display macros live in `templates/_fields.html` — `field_label` (the ONE field-type label map), `field_row`, `reach_icon`, `profile_header`. Don't fork copies back into individual templates; verify changes with `scripts/render_snapshot.py` (whitespace-normalized diff over 17 seeded pages).
- Phone labels (pass 2): `profile_fields.label` ('mobile'/'home'/'work'/custom text) via `ensure_profile_field_labels`; editor selects + custom input (`phone_label_select` macro); display via `label_display` (exposed as a Jinja global in `_make_jinja`).
- Direct-DB test writes need the columns/tables the app boot creates: run `TestClient(create_app(db))` BEFORE writing `quarter_status` etc. (boot runs `ensure_whitelist_schema`), and `store.init_db(db)` before touching `contacts`. `search_new_connections` degrades to [] when the contacts table is absent. `create_app` records its db path on `app.state.relmgr_db_path` (tests recover it for data-layer calls).
- Contact-list rows are per-CARD, carry NO email sub-line, and are one click target (overlay anchor, class `absolute inset-0`); badges are round 40px; filter tabs are multi-select `?f=<cardId|state>,…` (card group OR, state group OR, groups AND); `per_page=100`; sort = card name, state rank, name. Phones display via the `phone_fmt` Jinja global (`format_phone_display`, +1(XXX)XXX-XXXX, display-time only).

## Security contract (audit 2026-09-25, branch fm/whitelist-security-audit; re-audited 2026-09-26, branch fm/whitelist-security-audit-2)

- The 2026-09-26 re-audit (glm-5.3) re-verified S1-S7 fixed post-refactor and closed four more findings: FastAPI's default /docs /redoc /openapi.json are DISABLED at `create_app` (route-map disclosure — don't re-enable); `record_scan` caps the stored `?e=` at `_SCAN_EMAIL_MAX` (320) because GET /p + /s writes are outside the POST-only rate limiter; `get_profiles_needing_verification` binds `days` as a `datetime(?)` parameter (was an f-string); `forward_card` takes `owner_id` so forwards on curated stub pages mint grants the creating owner can decide (route passes `profile.owner_id`, same as the request path). Regression tests: `tests/test_security_audit2.py`.

- Owner self-view of /p/{handle} is AUTH-ONLY: signed `?ot=` owner_dashboard token (what My Profile's View-profile link carries, `profile_view_url`) or session cookie. NEVER treat `?e=` matching the owner's email as auth — that hole minted 365-day dashboard tokens (removed from `effective_tier` too). `?e=` stays the granted-CONTACT tracking param.
- EVERY /owner/{token}/ route that touches a grant must call `_verify_grant_ownership` — the quarter routes (make_permanent/revoke/punt) once skipped it (cross-owner IDOR). No route may fall back to `profiles ORDER BY id LIMIT 1` (bio-visibility used to).
- /photos/{pid}/{cid}[/hs] goes through `_photo_allowed`: default card, non-expired share-bundle cards, owner auth (`?t=` token or session; stub cards resolve via `profiles.owner_id`), or granted `?e=`. Owner templates append `?t={{ token }}` to photo imgs; profile.html granted view appends `?e=`.
- `create_app` installs one security middleware: body cap (16 MB), per-IP sliding-window limiter (POST /p/*/request|forward 10/min; /signin,/signup,/forgot-password 30/min; off via `WHITELIST_RATELIMIT_DISABLED` — parsed as an explicit truthy set 1/true/yes/on since the 2026-09-26 tool attack: `=0`/`=false` used to silently disable it), and Referrer-Policy/X-Content-Type-Options/X-Frame-Options/Permissions-Policy headers (capability tokens live in URLs). Session cookie sets `secure` when the request scheme is https. `_encode_square_jpeg` caps decodes at 40 MP (bomb guard); duplicate /p request POSTs no longer re-push owner email (`find_admitting_grant_id` tells new from deduped). `record_scan` bounds rows at `_SCAN_DAY_MAX` (500) per profile per UTC day (GET-speed `?e=` floods; A1's 320-char email cap only bounded row size). Regression tests: `tests/test_tool_attack.py`.
